# TimDo V2: Interactive Cloud-Native Project Board

## 1. Introduction

This document outlines the specification for TimDo V2, an interactive, cloud-native version of the project management application. V2 will enable users to log in, manage their projects dynamically through a web interface, and continue to generate the A3 SVG project poster. The application will leverage a serverless architecture, primarily using Cloudflare services, Next.js for the frontend, and Mantine for UI components.

## 2. Core Goals

*   **User Accounts & Authentication**: Secure user registration and login.
*   **Interactivity**: Allow users to create, read, update, delete (CRUD) and reorder projects.
*   **Real-time/Optimistic Updates**: Provide a fluid user experience with immediate feedback.
*   **Cloud-Native & Serverless**: Utilize cloud services for data storage and backend logic to ensure scalability and reduce operational overhead.
*   **Maintain SVG Poster Functionality**: Users should still be able to generate their project poster.
*   **Responsive Design**: Ensure usability across desktop and mobile devices.

## 3. Technology Stack

*   **Frontend**:
    *   Framework: Next.js (App Router)
    *   UI Library: Mantine
    *   Deployment: Cloudflare Pages
*   **Backend API**:
    *   Runtime: Cloudflare Workers
*   **Database**:
    *   Primary: Cloudflare D1 (SQL-based relational database)
    *   Alternative/Consideration: Cloudflare KV or Durable Objects for specific use-cases if D1 proves unsuitable for certain data patterns (e.g., highly dynamic user preferences not fitting a relational model well). D1 is preferred for core project data due to its relational nature.
*   **Authentication**:
    *   Provider: Auth0
    *   Integration: NextAuth.js (with Auth0 Provider) or Auth0 Next.js SDK.

## 4. Data Model (Cloudflare D1 Schema)

This section details the D1 database schema using SQL `CREATE TABLE` statements and references the corresponding TypeScript types.

### 4.1. User Table

Represents an authenticated user. The `id` will be the Auth0 user's `sub` (subject) claim.

```sql
CREATE TABLE IF NOT EXISTS Users (
  id TEXT PRIMARY KEY,                 -- Auth0 User ID (sub claim)
  email TEXT UNIQUE NOT NULL,
  name TEXT,
  created_at TEXT DEFAULT CURRENT_TIMESTAMP,
  updated_at TEXT DEFAULT CURRENT_TIMESTAMP
);

CREATE INDEX IF NOT EXISTS idx_users_email ON Users (email);
```

### 4.2. Project Table

Represents a single project or task belonging to a user.

```sql
CREATE TABLE IF NOT EXISTS Projects (
  id TEXT PRIMARY KEY,                         -- UUID generated by Worker
  user_id TEXT NOT NULL,                     -- Foreign Key referencing User.id
  project TEXT NOT NULL,
  reason TEXT,
  status TEXT NOT NULL CHECK (status IN ('do', 'delay', 'done', 'delegate')), -- For soft deletes, consider an 'is_deleted' flag or adding 'deleted' here.
  priority INTEGER NOT NULL DEFAULT 5 CHECK (priority BETWEEN 1 AND 10),
  size TEXT NOT NULL DEFAULT '***' CHECK (size IN ('*', '**', '***', '****', '*****')),
  notes TEXT,
  status_last_changed_on TEXT,               -- ISO 8601 datetime string
  is_deleted BOOLEAN DEFAULT FALSE,          -- For soft-delete implementation
  created_at TEXT DEFAULT CURRENT_TIMESTAMP,
  updated_at TEXT DEFAULT CURRENT_TIMESTAMP,
  FOREIGN KEY (user_id) REFERENCES Users(id) ON DELETE CASCADE
);

CREATE INDEX IF NOT EXISTS idx_projects_user_id ON Projects (user_id);
CREATE INDEX IF NOT EXISTS idx_projects_user_id_status ON Projects (user_id, status);
-- Index for soft deletes if implemented
CREATE INDEX IF NOT EXISTS idx_projects_user_id_is_deleted ON Projects (user_id, is_deleted);

```
*Note on `is_deleted` flag*: This provides a mechanism for soft deletion. API queries would typically filter for `is_deleted = FALSE`.

### 4.3. (Optional) BoardPreferences Table

User-specific preferences for their board display.

```sql
CREATE TABLE IF NOT EXISTS BoardPreferences (
  user_id TEXT PRIMARY KEY,                  -- Foreign Key referencing User.id
  theme TEXT DEFAULT 'auto' CHECK (theme IN ('light', 'dark', 'auto')),
  view_settings TEXT,                        -- JSON blob for other view preferences
  updated_at TEXT DEFAULT CURRENT_TIMESTAMP,
  FOREIGN KEY (user_id) REFERENCES Users(id) ON DELETE CASCADE
);
```

### 4.4. TypeScript Type Definitions (V2)

The corresponding TypeScript types (`UserV2`, `ProjectV2`, `ProjectV2Status`) for these database tables and API responses are defined in `app/types/project.types.ts`. These types will be shared between the Next.js frontend and the Cloudflare Workers backend.

## 5. Key Features & Functionality

### 5.1. User Authentication (Auth0 + NextAuth.js)

User authentication will be handled by Auth0, integrated into the Next.js application using `next-auth` (specifically, the Auth0 provider).

**Authentication Flow:**
1.  **Login Initiation**: User clicks a "Login" button in the Next.js app.
2.  **Redirect to Auth0**: The Next.js app, via `next-auth`, redirects the user to the Auth0 Universal Login page.
3.  **Auth0 Authentication**: User authenticates with Auth0 (e.g., username/password, social login).
4.  **Redirect to Application**: Upon successful authentication, Auth0 redirects the user back to a predefined callback URL in the Next.js application, providing an authorization code.
5.  **Token Exchange**: `next-auth` on the server-side exchanges this authorization code with Auth0 for an ID token, access token, and refresh token.
6.  **Session Creation**: `next-auth` creates a session for the user, typically storing the tokens (or a session reference) in a secure, HTTP-only cookie. The ID token contains user profile information (`sub`, `email`, `name`, etc.).
7.  **User Provisioning**:
    *   On first login, the application backend (Cloudflare Worker, triggered by a Next.js API route called after login) can use the `sub` (user ID) and other profile information from the ID token to create a new record in the `Users` table in D1 if one doesn't already exist.
    *   Subsequent logins will use the existing user record.
8.  **Authenticated Access**:
    *   For client-side requests to the backend API (Cloudflare Workers), the access token is retrieved from the `next-auth` session and included in the `Authorization: Bearer <accessToken>` header.
    *   Server-side components in Next.js can access user session data via `next-auth` helpers.

**API Authentication (Cloudflare Workers):**
*   All protected API endpoints on Cloudflare Workers will require a valid JWT access token.
*   A middleware on the Worker will:
    *   Extract the JWT from the `Authorization` header.
    *   Verify the JWT's signature using Auth0's public keys (JWKS URI).
    *   Validate claims (e.g., `iss` - issuer, `aud` - audience).
    *   If valid, extract the `sub` claim (Auth0 User ID) to identify the user for database operations.
    *   If invalid, return a 401 Unauthorized response.

*   User registration and login via Auth0 (supporting social logins if configured).
*   `theme`: TEXT (e.g., 'light', 'dark', 'auto')
*   `view_settings`: TEXT (JSON blob for other view preferences)
*   `updated_at`: TEXT DEFAULT CURRENT_TIMESTAMP

## 5. Key Features & Functionality

*   **Display**:
    *   Projects displayed in distinct columns based on their `status` ('do', 'delay', 'done', 'delegate').
    *   Each project card will show key information (project name, priority, size, etc.).
*   **Drag-and-Drop Reordering**:
    *   Users can drag projects to reorder them within the same status column. This will update the project's `priority`.
    *   Users can drag projects between different status columns (this will update the project's `status`, `status_last_changed_on`, and potentially `priority`).
    *   The `priority` field will be updated to reflect the new position.
*   **Filtering/Sorting**: (Beyond drag-and-drop)
    *   Initial sort within columns will be by `priority`.
    *   Consideration for additional client-side or server-supported sorting/filtering options (e.g., by priority, date created).
*   **Real-time/Optimistic Updates**:
    *   UI updates immediately upon user action (e.g., drag-and-drop, edit).
    *   Backend API calls made asynchronously to persist changes.
    *   Error handling for failed updates with rollback or user notification.

### 5.3. Project Management (CRUD)

*   **Create Project**:
    *   Modal or inline form to add a new project.
    *   Fields: `project` (name), `reason`, `status` (default to 'do'), `priority`, `size`, `notes`.
    *   New projects will be assigned a `priority` (e.g., based on the number of items in the target status column or a default value).
*   **Read/View Project Details**:
    *   Clicking a project card opens a modal or a detailed view displaying all project fields.
*   **Update Project Details**:
    *   Editable fields within the detail view/modal.
    *   Changes to `status` will also update `status_last_changed_on`.
*   **Delete Project**:
    *   Confirmation prompt before deletion.
    *   Soft delete: Projects can be marked as `is_deleted = TRUE` instead of being physically removed from the database. This allows for potential recovery and audit trails. API endpoints for fetching projects would typically exclude soft-deleted items unless explicitly requested.
    *   Hard delete: Projects are permanently removed. Simpler but offers no recovery.
    *   The choice depends on business requirements. The schema includes an `is_deleted` flag to support soft deletes.

### 5.4. SVG Poster Generation

*   A dedicated button/link to trigger SVG generation.
*   The Cloudflare Worker API will fetch all projects for the authenticated user from D1.
*   The existing `PrintableSvgPoster.tsx` component (or a refactored version) will be used, potentially server-side within a Worker or client-side after data fetch, to generate the SVG markup.
*   The generated SVG will be downloadable by the user, named appropriately (e.g., `username-projects-YYYY-MM-DD.svg`).
*   Sorting logic within the SVG for "Done" projects (by `status_last_changed_on` then `priority`) will be maintained.

### 5.5. Responsive Design

*   The application interface, including project boards and modals, will be fully responsive and usable on desktop, tablet, and mobile devices using Mantine's responsive styling capabilities.
*   Drag-and-drop functionality will be touch-friendly.

## 6. API Design (Cloudflare Workers)

The API will be RESTful, with endpoints secured by Auth0 JWTs. Cloudflare Workers will handle requests, interact with D1, and return JSON responses.

*   **Authentication**: Middleware in Workers to verify JWTs and extract `user_id`.
*   **Base Path**: `/api/v2/`

### Project Endpoints:

*   `GET /api/v2/projects`:
    *   Description: Fetches all non-deleted projects for the authenticated user.
    *   Response: Array of `Project` objects.
*   `POST /api/v2/projects`:
    *   Description: Creates a new project for the authenticated user.
    *   Request Body: `Project` data (excluding `id`, `user_id`, `created_at`, `updated_at` - server assigns). `priority` should be provided or will be set to a default.
    *   Response: The created `Project` object.
*   `GET /api/v2/projects/{projectId}`:
    *   Description: Fetches a specific project by its ID. User must own the project.
    *   Response: Single `Project` object.
*   `PUT /api/v2/projects/{projectId}`:
    *   Description: Updates an existing project. User must own the project.
    *   Request Body: Partial or full `Project` data to update. If `status` changes, `status_last_changed_on` is updated. `priority` can also be updated here.
    *   Response: The updated `Project` object.
*   `DELETE /api/v2/projects/{projectId}`:
    *   Description: Deletes a project (or marks as 'deleted'). User must own the project.
    *   Response: Success/failure message.
*   `POST /api/v2/projects/batch-update-priority`:
    *   Description: Updates the `priority` and potentially `status` for multiple projects, typically after a drag-and-drop operation affecting several items.
    *   Request Body: Array of objects like `{ projectId: string, newPriority: number, newStatus?: ProjectStatus }`.
    *   Response: Success/failure message or array of updated projects.

### User Endpoints:

*   `GET /api/v2/users/me`:
    *   Description: Fetches profile information for the authenticated user.
    *   Response: User object (`id`, `email`, `name`).

### SVG Poster Endpoint:

*   `GET /api/v2/svg-poster`:
    *   Description: Generates and returns the data required for the SVG poster for the authenticated user. This might return JSON data for client-side SVG rendering or the full SVG string if rendered server-side by the worker.
    *   Response: JSON array of `ProjectV2` objects (filtered for `is_deleted = FALSE`) or SVG string.

## 6. Detailed Technical Decisions

### 6.1. ORM/Query Builder for Cloudflare D1

While D1 allows direct SQL execution, using a type-safe query builder or a lightweight ORM can improve developer experience, reduce boilerplate, and enhance type safety.

*   **Recommendation**: **Drizzle ORM**
    *   **Rationale**:
        *   **TypeScript First**: Excellent type safety and autocompletion.
        *   **D1 Support**: Officially supports Cloudflare D1.
        *   **Lightweight**: Generates efficient SQL, suitable for serverless environments like Cloudflare Workers.
        *   **Schema-driven**: Define schema in TypeScript, Drizzle generates migrations (or SQL schema files).
        *   **Developer Experience**: Modern API, active development.
    *   **Alternatives Considered**:
        *   **Kysely**: Another excellent type-safe SQL query builder. Less of an "ORM" than Drizzle.
        *   **Prisma**: More feature-rich ORM, but can be heavier. D1 support is via a driver adapter.
        *   **Raw D1 Client**: Most direct, but lacks type safety for queries and results.

### 6.2. Client-Side Data Management

For managing server state, caching, optimistic updates, and background synchronization in the Next.js frontend.

*   **Recommendation**: **TanStack Query (formerly React Query)**
    *   **Rationale**:
        *   **Server State Management**: Specifically designed for fetching, caching, and updating data from a server.
        *   **Caching & Synchronization**: Robust caching mechanisms, background refetching, and stale-while-revalidate strategies.
        *   **Optimistic Updates**: Simplifies implementing UI changes that appear instant to the user while data is being persisted in the background.
        *   **Developer Experience**: Widely adopted, excellent documentation, and hooks-based API.
        *   **Devtools**: Powerful developer tools for inspecting query states and cache.
    *   **Usage**: Will be used to fetch project data, handle mutations (create, update, delete projects), and manage the state of the interactive project board.

## 10. Security Considerations

*   **Authentication**: All API endpoints modifying or accessing user-specific data must be protected and require a valid JWT from Auth0.
*   **Authorization**: Workers must verify that the authenticated user (`user_id` from JWT) is authorized to access/modify the requested resources (e.g., a user can only modify their own projects).
*   **Input Validation**: All incoming data to API endpoints must be rigorously validated on the server-side (Worker) to prevent injection attacks or data corruption.
*   **CORS**: Configure CORS policies on Cloudflare Workers if the API is accessed from different domains (though typically Next.js frontend and Workers API will be under the same effective origin or configured for proxying).
*   **HTTPS**: Enforced by Cloudflare Pages and Workers.
*   **Secrets Management**: Securely manage Auth0 client secrets, API keys, and database credentials using Cloudflare's secrets management.

**12.1.1. Drizzle ORM Setup (`workers/src/db/`)**

*   **`schema.ts`**: Define Drizzle schemas for `Users`, `Projects`, and `BoardPreferences` tables as outlined in Section 4. Example for `Projects`:
    ```typescript
    // workers/src/db/schema.ts
    import { sql } from 'drizzle-orm';
    import { text, integer, sqliteTable, uniqueIndex } from 'drizzle-orm/sqlite-core';

    export const users = sqliteTable('Users', {
      id: text('id').primaryKey(), // Auth0 User ID (sub claim)
      email: text('email').notNull().unique(),
      name: text('name'),
      createdAt: text('created_at').default(sql`CURRENT_TIMESTAMP`),
      updatedAt: text('updated_at').default(sql`CURRENT_TIMESTAMP`),
    });

    export const projects = sqliteTable('Projects', {
      id: text('id').primaryKey(), // UUID
      userId: text('user_id').notNull().references(() => users.id, { onDelete: 'cascade' }),
      project: text('project').notNull(),
      reason: text('reason'),
      status: text('status').notNull().default('do'), // 'do', 'delay', 'done', 'delegate'
      priority: integer('priority').notNull().default(5), // 1-10
      size: text('size').notNull().default('***'), // '*', '**', '***', '****', '*****'
      notes: text('notes'),
      statusLastChangedOn: text('status_last_changed_on'), // ISO 8601 datetime string
      isDeleted: integer('is_deleted', { mode: 'boolean' }).default(false), // Soft delete
      createdAt: text('created_at').default(sql`CURRENT_TIMESTAMP`),
      updatedAt: text('updated_at').default(sql`CURRENT_TIMESTAMP`),
    }
    // Add indexes as defined in Section 4.2 using Drizzle syntax if needed,
    // though D1 indexes are primarily managed via SQL in migrations.
    );
    // ... other schemas (BoardPreferences)
    ```
*   **`index.ts` (Drizzle client)**:
    ```typescript

    import * as schema from './schema';

    export const getDb = (d1Binding: D1Database) => drizzle(d1Binding, { schema });
    ```

**12.1.2. CRUD Operations Example: Projects**

**A. Create Project (`POST /api/v2/projects`)**

1.  **Route (`workers/src/routes/projects.ts`)**:
    *   Define a Hono route for `POST /`.
    *   Apply authentication middleware (see 12.2.5).
    *   Use a validation middleware (e.g., `zodValidator` from `@hono/zod-validator`) with a Zod schema for the request body.
    *   Call the `projectService.createProject` function.
    ```typescript
    // workers/src/routes/projects.ts
    import { Hono } from 'hono';
    import { zValidator } from '@hono/zod-validator';
    import { projectCreateSchema } from '../validators/projectValidators'; // Zod schema
    import { createProject } from '../services/projectService'; // Assuming getProjectsForUser is also here
    import { authMiddleware } from '../middleware/auth'; // Your auth middleware
    import { Env } from '../index'; // For environment typings including DB binding

    const projectsApp = new Hono<{ Bindings: Env }>();

    projectsApp.use('*', authMiddleware); // Apply auth to all project routes

    projectsApp.post('/', zValidator('json', projectCreateSchema), async (c) => {
      const projectData = c.req.valid('json');
      const userId = c.get('userId'); // Set by authMiddleware
      const db = c.get('db'); // Set by a global middleware or passed directly
      const newProject = await createProject(db, userId, projectData);
      return c.json(newProject, 201);
    });
    // ... other project routes (GET, PUT, DELETE)
    export default projectsApp;
    ```

2.  **Validator (`workers/src/validators/projectValidators.ts`)**:
    ```typescript
    // workers/src/validators/projectValidators.ts
    import { z } from 'zod';
    import { ProjectV2Status, ProjectSize } from '@/app/types/project.types'; // Assuming path alias

    const statusValues: [ProjectV2Status, ...ProjectV2Status[]] = ['do', 'delay', 'done', 'delegate'];
    const sizeValues: [ProjectSize, ...ProjectSize[]] = ['*', '**', '***', '****', '*****'];

    export const projectCreateSchema = z.object({
      project: z.string().min(1),
      reason: z.string().optional(),
      status: z.enum(statusValues).default('do'),
      priority: z.number().int().min(1).max(10).default(5),
      size: z.enum(sizeValues).default('***'),
      notes: z.string().optional(),
    });
    export type ProjectCreatePayload = z.infer<typeof projectCreateSchema>;
    ```

3.  **Service (`workers/src/services/projectService.ts`)**:
    *   Contains business logic.
    *   Generates a UUID for the new project.
    *   Uses Drizzle ORM to insert the project into the D1 database.
    ```typescript
    // workers/src/services/projectService.ts
    import { v4 as uuidv4 } from 'uuid';
    import { projects as projectsTable } from '../db/schema';
    import { ProjectCreatePayload } from '../validators/projectValidators';
    import type { DrizzleD1Database } from 'drizzle-orm/d1';
    import * as schema from '../db/schema'; // Import all schemas

    type DB = DrizzleD1Database<typeof schema>;

    export async function createProject(db: DB, userId: string, data: ProjectCreatePayload) {
      const projectId = uuidv4();
      const newProjectData = {
        id: projectId,
        userId,
        ...data,
        statusLastChangedOn: data.status ? new Date().toISOString() : undefined,
        // isDeleted, createdAt, updatedAt have defaults in schema/DB
      };
      const result = await db.insert(projectsTable).values(newProjectData).returning();
      return result[0];
    }
    // ... other service functions (get, update, delete)
    ```

**B. Read Projects (`GET /api/v2/projects`)**

1.  **Route**: Define `GET /` in `projects.ts`.
2.  **Service**:
    *   Function `getProjectsForUser(db, userId)`.
    *   Uses Drizzle: `db.select().from(projectsTable).where(and(eq(projectsTable.userId, userId), eq(projectsTable.isDeleted, false)))`.
    *   Consider pagination if the number of projects can be large.

**C. Update Project (`PUT /api/v2/projects/{projectId}`)**

1.  **Route**: Define `PUT /:projectId` in `projects.ts`.
2.  **Validator**: Schema for updatable fields.
3.  **Service**:
    *   Function `updateProject(db, userId, projectId, data)`.
    *   Verify user ownership: Fetch project first, check `userId`.
    *   If `status` changes, update `statusLastChangedOn`.
    *   Set `updatedAt` to current timestamp.
    *   Uses Drizzle: `db.update(projectsTable).set({...data, updatedAt: new Date().toISOString()}).where(and(eq(projectsTable.id, projectId), eq(projectsTable.userId, userId))).returning()`.

**D. Delete Project (`DELETE /api/v2/projects/{projectId}`)**

1.  **Route**: Define `DELETE /:projectId` in `projects.ts`.
2.  **Service**:
    *   Function `deleteProject(db, userId, projectId)`.
    *   Verify user ownership.
    *   Soft delete: `db.update(projectsTable).set({ isDeleted: true, updatedAt: new Date().toISOString() }).where(and(eq(projectsTable.id, projectId), eq(projectsTable.userId, userId)))`.
    *   Hard delete (if preferred): `db.delete(projectsTable).where(and(eq(projectsTable.id, projectId), eq(projectsTable.userId, userId)))`.

**12.1.3. User Provisioning Endpoint (Worker)**
A dedicated endpoint in the worker (e.g., `POST /api/v2/users/ensure`) will be called by the Next.js `signIn` callback.
*   **Route (`workers/src/routes/user.ts`)**:
    ```typescript

    import { zValidator } from '@hono/zod-validator';
    import { ensureUserSchema } from '../validators/userValidators'; // Zod schema for user data

    // from Next.js backend, or it could be protected by a secret header.
    // For simplicity, if called by Next.js backend, it might not need full user JWT auth.

        const userData = c.req.valid('json');
    ```

*   **Service (`workers/src/services/userService.ts`)**:
    ```typescript
    // workers/src/services/userService.ts
    import { users as usersTable } from '../db/schema';
    import type { DrizzleD1Database } from 'drizzle-orm/d1';
    import * as schema from '../db/schema';
    import { eq } from 'drizzle-orm';

    type DB = DrizzleD1Database<typeof schema>;
    interface UserEnsurePayload {
      id: string; // Auth0 sub
      email: string;
      name?: string;
    }

    export async function ensureUser(db: DB, data: UserEnsurePayload) {
      const existingUser = await db.select().from(usersTable).where(eq(usersTable.id, data.id)).get();
      if (existingUser) {
        // Optionally update name/email if changed, though Auth0 is source of truth
        // For now, just return existing user
        return existingUser;
      }
      const newUser = {
        id: data.id,
        email: data.email,
        name: data.name,
        // createdAt, updatedAt have defaults
      };
      const result = await db.insert(usersTable).values(newUser).returning();
      return result[0];
    }
    ```

### 12.2. Auth0 Integration - Detailed Flow

This expands on Section 5.1.

**12.2.1. User Registration (Auth0 Universal Login)**
1.  **Initiation (Next.js Frontend)**: User clicks a "Sign Up" button. This button can call `signIn('auth0', { screen_hint: 'signup' })` from `next-auth/react`.
2.  **Redirect to Auth0**: `next-auth` redirects the browser to your Auth0 Universal Login page, with `screen_hint=signup` potentially taking them directly to the sign-up tab.
3.  **Auth0 Registration**: User fills out the registration form on Auth0's page (email, password, any other required fields configured in Auth0).
4.  **Auth0 User Creation**: Auth0 creates the user in its own user database.
5.  **Redirect to Application**: Auth0 redirects the user back to the `NEXTAUTH_URL/api/auth/callback/auth0` endpoint in your Next.js app, providing an authorization code.

**12.2.2. User Login (Auth0 Universal Login)**
1.  **Initiation (Next.js Frontend)**: User clicks a "Login" button. This button calls `signIn('auth0')` from `next-auth/react`.
2.  **Redirect to Auth0**: `next-auth` redirects to Auth0 Universal Login.
3.  **Auth0 Authentication**: User authenticates (e.g., email/password, social login if configured in Auth0).
4.  **Redirect to Application**: Auth0 redirects back to `NEXTAUTH_URL/api/auth/callback/auth0` with an authorization code.

**12.2.3. Next.js Session Management (`app/api/auth/[...nextauth]/route.ts`)**
1.  **Callback Handling**: The `route.ts` file handles the `/api/auth/callback/auth0` request.
    ```typescript
    // app/api/auth/[...nextauth]/route.ts
    import NextAuth, { NextAuthOptions } from 'next-auth';
    import Auth0Provider from 'next-auth/providers/auth0';

    // This function would make a fetch call to your Worker API's user creation/ensure endpoint.
    // It should be defined in a way that it can be called from this server-side NextAuth callback.
    // For example, in a separate file like `@/lib/server/userActions.ts`
    async function ensureUserInD1(userData: { id: string; email: string; name?: string }) {
      const workerApiBaseUrl = process.env.WORKER_API_BASE_URL_INTERNAL || process.env.NEXT_PUBLIC_WORKER_API_BASE_URL;
      // WORKER_API_BASE_URL_INTERNAL would be for direct network calls if Next.js and Worker are in same infra
      // NEXT_PUBLIC_WORKER_API_BASE_URL for public calls.
      // Ensure this call is secure, e.g. using a secret header if the endpoint isn't user-JWT protected.
      const response = await fetch(`${workerApiBaseUrl}/users/ensure`, {
        method: 'POST',
        headers: {
          'Content-Type': 'application/json',
          // 'X-Internal-Secret': process.env.INTERNAL_API_SECRET, // Example for securing internal call
        },
        body: JSON.stringify(userData),
      });
      if (!response.ok) {
        const errorBody = await response.text();
        throw new Error(`Failed to ensure user in D1: ${response.status} ${errorBody}`);
      }
      return response.json();
    }

    export const authOptions: NextAuthOptions = {
      providers: [
        Auth0Provider({
          clientId: process.env.AUTH0_CLIENT_ID!,
          clientSecret: process.env.AUTH0_CLIENT_SECRET!,
          issuer: process.env.AUTH0_ISSUER!,
          authorization: { params: { scope: "openid email profile" } }, // Ensure profile scope for name
        }),
      ],
      session: {
        strategy: 'jwt', // Use JWTs for session
      },
      callbacks: {
        async jwt({ token, user, account }) {
          if (account && user) {
            token.accessToken = account.access_token;
            token.id = user.id; // Auth0 'sub' is mapped to 'user.id' by NextAuth
          }
          return token;
        },
        async session({ session, token }) {
          session.accessToken = token.accessToken as string;
          session.user.id = token.id as string; // Add Auth0 'sub' to session.user.id
          return session;
        },
        async signIn({ user, account, profile }) {
          // 'user.id' is Auth0 'sub'. 'user.email' and 'user.name' are from Auth0 profile.
          if (user.id && user.email) {
            try {
              await ensureUserInD1({
                id: user.id,
                email: user.email,
                name: user.name || undefined,
              });
              console.log(`User ${user.id} (${user.email}) signed in and provisioned/verified in D1.`);
            } catch (error) {
              console.error("Failed to provision user in D1 during signIn:", error);
              // Decide if sign-in should fail if provisioning fails.
              // Returning false would prevent sign-in.
              // For a robust system, you might want to return false or redirect to an error page.
              return false;
            }
          } else {
            console.error("Auth0 user data missing id or email in signIn callback.");
            return false; // Prevent sign-in if essential Auth0 data is missing
          }
          return true; // Continue sign in
        },
      },
      // secret: process.env.NEXTAUTH_SECRET, // Handled by NEXTAUTH_SECRET env var
    };

    const handler = NextAuth(authOptions);
    export { handler as GET, handler as POST };
    ```
2.  **Token Exchange**: `next-auth` exchanges the authorization code with Auth0 for an ID token, Access token, and Refresh token.
3.  **Session Creation**: `next-auth` creates a JWT session token, storing relevant claims (like the access token for your API and user ID). This JWT is stored in a secure, HTTP-only cookie.
4.  **User Provisioning in D1 `Users` Table**:
    *   User provisioning in the D1 `Users` table is handled within the `signIn` callback of `next-auth` (as detailed in the `authOptions` example above).
    *   Immediately after a successful Auth0 authentication and before the Next.js session is fully established, the `signIn` callback is triggered.
    *   Inside this callback, the `ensureUserInD1` function is called. This function makes a `fetch` request to a dedicated Cloudflare Worker endpoint (e.g., `POST /api/v2/users/ensure`).
    *   The worker endpoint checks if the user (identified by their Auth0 `sub`) exists in the D1 `Users` table. If not, it creates a new record using their `id` (Auth0 `sub`), `email`, and `name` obtained from the Auth0 profile.
    *   This approach ensures that a corresponding user record in D1 is present before the user starts interacting with features that rely on it. If provisioning fails, the `signIn` callback can prevent login.

**12.2.4. Authenticated API Requests (Next.js Frontend to Cloudflare Worker API)**

**12.2.5. API Authorization (Cloudflare Worker - `workers/src/middleware/auth.ts`)**
This middleware will be applied to protected Hono routes.
```typescript
// workers/src/middleware/auth.ts
import { Context, Next } from 'hono';
import { jwtVerify, createRemoteJWKSet } from 'jose'; // Using 'jose' library for JWT validation
import { Env } from '../index'; // Worker environment types

export async function authMiddleware(c: Context<{ Bindings: Env }>, next: Next) {
  const authHeader = c.req.header('Authorization');
  if (!authHeader || !authHeader.startsWith('Bearer ')) {
    return c.json({ error: 'Unauthorized', message: 'Missing or invalid Authorization header' }, 401);
  }

  const token = authHeader.substring(7); // Remove "Bearer "
  if (!token) {
    return c.json({ error: 'Unauthorized', message: 'Missing token' }, 401);
  }

  const JWKS = createRemoteJWKSet(new URL(`https://${c.env.AUTH0_DOMAIN}/.well-known/jwks.json`));

  try {
    const { payload } = await jwtVerify(token, JWKS, {
      issuer: `https://${c.env.AUTH0_DOMAIN}/`,
      audience: c.env.AUTH0_AUDIENCE,
    });

    if (!payload.sub) {
      return c.json({ error: 'Unauthorized', message: 'Token missing subject (sub) claim' }, 401);
    }

    c.set('userId', payload.sub); // Set userId in context for downstream handlers

    // User provisioning is handled by the Next.js signIn callback (Section 12.2.3).
    // The worker API assumes a user record exists in D1 if authentication is successful
    // because the Next.js backend is responsible for creating it via the /api/v2/users/ensure endpoint.

    await next();
  } catch (err: any) {
    console.error("JWT Verification Error:", err.message);
    // Provide more specific error messages based on the type of error if possible
    let errorMessage = `Token validation failed: ${err.message}`;
    if (err.code === 'ERR_JWKS_TIMEOUT') {
        errorMessage = 'JWKS endpoint timed out. Cannot verify token.';
    } else if (err.code === 'ERR_JWS_INVALID') {
        errorMessage = 'JWS is invalid. Token malformed or signature invalid.';
    } else if (err.code === 'ERR_JWT_EXPIRED') {
        errorMessage = 'Token has expired.';
    } else if (err.code === 'ERR_JWT_CLAIM_VALIDATION_FAILED') {
        errorMessage = `Token claim validation failed: ${err.claim} ${err.reason}.`;
    }
    return c.json({ error: 'Unauthorized', message: errorMessage }, 401);
  }
}
```
